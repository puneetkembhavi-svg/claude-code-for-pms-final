03
Rewind

The recovering number was hiding a worsening one

Acceptance rate looked like it was healing — 54% back to 73%. It was healing because the system had simply stopped asking the people it might lose. The spread between busiest and quietest responder tripled, 2.4 → 7.0, and kept climbing the whole time.

Analyze this dataset callout history and identify the 3–5 biggest drivers of 4.2 failure. Segment the results by all known vectors. Quantify each driver, flag anomalies, and explain what changed and why it matters. Finish with the 3 most important actions I should investigate as the PM.

04
X-Ray Vision

One way up, no way back on its own

Exactly one function in the entire codebase ever adds points back to a responder's standing — and only on a successful, in-time accept. No decay. No timer. No reset. A responder already locked out has no path back except luck.

Find me the part of this code that takes points off somebody when they miss a ping or turn one down. Show it to me and explain it in plain English. Then find me every single thing in this code that puts points back on.

03 · What stops this happening again

review-checklist: the same four questions, every brief, every time

4.2 shipped without a named test owner, without a stated success measure, and — per Helen's own note — almost got "fixed" by quietly flipping a number instead of explaining the problem first. This skill checks for exactly that pattern before a brief goes anywhere.

CHECK 1
Owner named
Someone specific is holding it — not just consulted, not "whoever picks it up."
CHECK 2
Success measure
States how anyone would know it worked — a signal, not just a description.
CHECK 3
Scope stays bounded
What's promised at the end matches what was framed at the start.
CHECK 4
Problem before fix
The problem is explained before the solution is pitched — order, not just content.
0 9 * * 1 Every Monday, 9am — re-reads every brief in the repo and reports the full checklist back automatically. Fires regardless of whether anything's changed.
The tell, in hindsight: Marcus asked the exact right question in #dispatch-team the day after 4.2 shipped — "does the config distinguish declining from timing out?" — and it just sat there, unanswered, for weeks. Not a testing failure. A process one. That's precisely the gap review-checklist exists to close before it ships next time, not after.
